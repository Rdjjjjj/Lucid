# Lucid 最终方案总览

- 版本：0.3
- 日期：2026-10-17
- 状态：方案已对齐，待实现验证
- 当前阶段：只整理方案，不开始代码迁移
- 参考项目：[青简输入法 REA 逆向分析报告](research/qingjian-rea/README.md)

这份文档是 Lucid 当前四部分方案的统一入口。它规定产品要做什么、各部分如何配合、第一阶段使用什么技术，以及怎样验收和发布。

## 1. 产品定位和范围

Lucid 是面向中文母语英文学习者的桌面英文输入法。用户正常输入英文；遇到不会拼写的英文单词时，可以输入拼音字母作为临时占位。用户完成句子后，AI 给出修改建议，用户确认后才替换原文。

首版优化现有 macOS 桌面 App，Windows 作为后续平台。Lucid 只负责英文输入，不提供中文输入法、中文候选或整句中文翻译输入。双语伴学和中文翻转能力保留为辅助功能，但不能改变英文输入和确认替换的核心流程。

覆盖目标是常见打字场景。微信、钉钉、记事本和 MonkeyAI 是首轮重点验证对象，之后再扩展到浏览器、邮件、文档和其他文本输入框。

## 2. 用户使用流程

1. 用户在支持的文本输入框中输入英文。
2. 不会拼写单词时，用拼音字母暂时占位。
3. 输入句末标点，或者停止输入约两秒，Lucid 判断是否形成完整句子。
4. Lucid 只把当前待处理句子发送给用户配置的 AI 服务，输入字符继续立即上屏。
5. AI 完整返回后，显示一张只包含一条主要建议的卡片。
6. 用户可以选择“替换”“保留原文”或“查看修改”。
7. 点击替换前，Lucid 再次核对输入框、原文、替换范围和请求版本；不能可靠核对时不替换，并说明原因。

句末判断要避开网址、小数和常见缩写中的句号。一次输入包含多句话时，每句话分别处理。AI 无需修改时显示“无需修改”后关闭卡片；AI 失败时保留原文并显示具体报错原因，用户可以用当前最新原文重试。

用户继续输入、移动光标、修改原文、切换窗口或切换输入框后，旧建议立即失效。AI 处理期间可以继续打字，网络请求不能阻塞输入。

## 3. 聊天软件规则

Lucid 不自动发送消息，也不改变聊天软件原有的回车行为。微信和钉钉测试必须停留在输入框草稿状态，不向其他人发送消息。

用户输入句末标点后可以等待建议；用户直接按回车时，仍由聊天软件按照自身规则处理。无法可靠读取或替换某个聊天软件的文本时，Lucid 不执行替换并提示不支持原因，后续可以为重点聊天软件增加专门适配逻辑。

## 4. 产品架构

Lucid 采用“平台外壳 + 共享 Core + Provider”的结构：

```text
当前应用
  ↓ 系统输入法事件
平台外壳（macOS InputMethodKit / Windows TSF）
  ↓ 平台无关事件
Lucid Core（Session、句子判断、请求生命周期、建议有效性）
  ↓ CorrectionProvider
HTTP Provider（OpenAI 兼容 / Anthropic 兼容）
  ↓ 用户配置的服务地址
AI 服务
```

平台外壳负责接收系统事件、让文字进入当前应用、读取焦点和文本范围、显示卡片以及执行经过校验的替换。Core 是统一状态拥有者，不依赖具体操作系统、界面或 AI 服务商。Provider 负责网络请求和响应解析，不直接操作文本，也不决定是否替换。

建议只属于生成它的输入框和句子。任何文本变化、焦点变化或版本不匹配都必须让建议失效。

## 5. 技术栈和进程边界

### 5.1 共同技术选择

- Rust 2024 是唯一正式开发语言。
- Cargo Workspace 是正式构建入口。
- Core 负责 `Engine`、`InputSession`、句末判断、请求调度、结果有效性和替换前置条件。
- `lucid-provider-http` 负责 `reqwest`、OpenAI 兼容协议、Anthropic 兼容协议、超时和错误转换。
- Core 不依赖 `reqwest`、Tokio、具体 AI 服务商或 API Key 存储。
- 日志只记录请求元数据、耗时和错误类别，不记录句子正文、按键内容或 API Key。
- 不保存输入历史，只发送当前待处理句子。

### 5.2 macOS 首版

- 使用 Rust、`objc2` 和 InputMethodKit。
- 输入法进程内运行平台外壳、Core 和后台 Provider。
- 首版不额外增加本地 Server。
- 设置 App 独立运行，负责配置存储和启用引导，不参与日常输入。
- 首版优先支持 Apple Silicon，最低 macOS 13；Intel 后续再评估。
- API Key 和普通配置都使用 Lucid 专用的 macOS 用户默认值，输入法读取时不会触发钥匙串授权弹窗。

### 5.3 Windows 后续

- 使用 TSF DLL、独立 Server 和 Settings。
- TSF DLL 只负责 TSF/COM、文档读写、范围校验和通信，不直接访问网络。
- Server 负责 Core、Session 和 Provider。
- TSF DLL 与 Server 使用 Named Pipe 和带长度前缀的 JSON 帧通信。
- API Key 使用 DPAPI 或 Credential Manager。
- Windows 当前只做规划，不纳入首版实现和验收。

### 5.4 状态和请求

每个输入框拥有独立 Session，至少包含：

- `session_id`：输入框生命周期；
- `request_id`：请求序号；
- `text_version`：原文版本；
- 当前焦点、句子原文和替换范围；
- 当前建议状态。

AI 返回必须同时匹配 `session_id + request_id + text_version`。不匹配的结果直接丢弃。

## 6. 测试验收方案

首版以 macOS 实机验收为准，重点顺序如下：

1. TextEdit/记事本：英文立即上屏、拼音占位、句末触发、停顿触发、建议显示和确认替换。
2. 微信、钉钉、MonkeyAI：输入延迟、句末处理、建议卡片、替换可靠性和回车行为。
3. 浏览器、邮件、文档和其他文本输入框：跨应用兼容性。
4. 异常场景：网络失败、AI 返回错误、超时、空结果、无需修改、切换焦点、移动光标、继续输入和文本被外部修改。
5. 安全场景：密码框和安全输入框不处理，日志不出现正文和密钥。

微信和钉钉的测试只允许在本地草稿输入框中进行。测试人员不得按下会导致消息发送的回车，也不得向其他人发送测试消息。

通过标准是：普通输入不被 AI 阻塞；AI 失败时原文保留并给出原因；旧结果不能误替换新文本；确认替换准确；无法可靠替换时不执行危险操作；聊天软件原有发送行为不被 Lucid 改写。

## 7. 安装和发布方案

macOS 主要使用 `.pkg` 安装包。安装包负责复制 App、安装到系统输入法目录、注册输入源，并支持后续升级和清理。

当前签名策略参考青简输入法：App 使用 ad-hoc 签名，安装包暂不使用 Developer ID 签名和 Apple 公证。这个方案适合当前个人验证和早期测试；用户安装时可能看到 macOS 安全提示，需要按安装说明手动允许。面向更广泛用户发布前，再单独评估正式签名和公证。

Windows 安装包和正式发布延后到 Windows 实机方案确定后处理。

## 8. 实施顺序

1. 以本总览和四份详细文档作为实现依据。
2. 统一 Cargo Workspace、CI、安装脚本和 macOS 打包入口。
3. 将 HTTP 和服务商解析从 Core 拆到 `lucid-provider-http`。
4. 补齐 Core 的 Session、句子触发、请求版本和替换校验。
5. 完成 macOS 配置存储和设置引导。
6. 先在记事本、微信、钉钉和 MonkeyAI 完成实机验收。
7. macOS 闭环稳定后，再处理 Windows TSF、Server 和安装器。
8. Rust 闭环稳定后，将 Swift/Xcode 旧实现从正式构建、CI 和发布流程中移除或归档。
